# Size and memory baseline

## Image

v1 (806638e):

```
28174113 bytes
```

v2 (this branch, Task 9.1, `docker build -t smtp-gateway:v2-local --build-arg
VERSION=v2-local .` on the ARM64 host, single-arch local build, 2026-11-17):

```
39478550 bytes uncompressed (docker image inspect --format '{{.Size}}')
10791521 bytes compressed   (docker save smtp-gateway:v2-local | gzip | wc -c)
```

Compressed size 10.79 MB is well under the 25 MB (25,000,000 byte) budget
(section 2.5), with about 14.2 MB of headroom. The uncompressed figure is
above the plan's "Verify locally" rough estimate of 30,000,000 bytes
(expected, see the Task 9.1 commit's deviation note: the embedded React SPA,
GORM, Goose and the pure-Go SQLite driver all add bytes the v1 image didn't
have), but the actual gate — compressed size — passes with room to spare.
This is a single-arch (arm64) local build; the multi-arch CI build (Task
9.3, out of scope here) will push `linux/amd64,linux/arm64,linux/arm/v7`
manifests, each measured the same way by the registry.

## Memory

v1 (806638e):

```
smtp-gateway 20.24MiB / 64MiB
```

v2 (this branch, Task 8.4, `tools/smoke start && sleep 20 && docker stats`,
ARM64 host `angw-us-phoenix-1-arm`, 2026-11-17):

```
6.812MiB / 23.41GiB
```

(The smoke container has no `mem_limit`, unlike the production
`docker-compose.yml`, so the second number is the host's total memory, not a
container limit; it is not comparable to the v1 `/64MiB` figure. The RSS itself
is not like-for-like either: v1's 20 MiB is the live container after weeks of
real SMTP and panel traffic, while v2's figure is a cold start 20 s after boot
with an unreachable upstream and OIDC issuer and no requests. Re-measure v2
under real traffic in Task 9.3/9.4 before comparing.) Idle RSS
6.8 MiB is well under the 40 MiB budget (section 2.5), so Task 9.2/9.4's
compose `mem_limit`/`GOMEMLIMIT` do **not** need raising past the plan's
defaults — 6.8 MiB is nowhere near the 40–56 MiB range that would require it.

Against the plan's expected orders of magnitude (section 8.1): `Authenticate`
27.2 µs, well under the 100 µs budget — the once-a-minute `LastUsedAt` touch

ms and `ListWhileWriting` (listing while a goroutine records continuously on
the single-writer pool) 0.43 ms: both close to plain `List`, confirming the
panel's read pool does not queue behind SMTP writes.
